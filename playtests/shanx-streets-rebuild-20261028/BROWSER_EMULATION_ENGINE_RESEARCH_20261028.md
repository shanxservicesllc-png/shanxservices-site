## Verified research paths
1. **Play! PS2 emulator:** Experimental native and browser execution of PlayStation 2 binaries shows how a console's computation can be implemented with JS/Wasm and browser graphics. Emulator is not a modifiable original-game source engine. https://playjs.purei.org/ ; https://github.com/jpd002/play-
2. **RPCS3 PS3 emulator:** Proven native C++ approach, complex hardware emulation; the browser Wasm fork is a research claim, not a tested basis for an Android browser game. https://rpcs3.net/ ; https://github.com/rtmtree/rpcs3-wasm
3. **Xenia Canary Xbox 360 emulator:** Native hardware emulation; use as a systems reference, not browser delivery engine. https://github.com/xenia-canary/xenia-canary
4. **PlayCanvas browser engine:** WebGL/WebGPU renderer, entity/component architecture, animation state graphs for rigged models and touch-ready application building. Existing game engine rather than custom renderer/physics. https://github.com/playcanvas/engine ; https://developer.playcanvas.com/user-manual/animation/
5. **PlayCanvas physics:** ammo.js/Bullet WebAssembly rigid bodies and collision components; *physics must be activated, not assumed present*. https://developer.playcanvas.com/user-manual/physics/ ; https://developer.playcanvas.com/en/user-manual/physics/physics-basics/
6. **Existing raycast vehicle physics:** Official PlayCanvas desktop/mobile project with suspension, steering, wheel behavior using Ammo's raycast vehicle API, a foundational proven subsystem we can learn from and adapt with its actual source/license. https://developer.playcanvas.com/tutorials/vehicle-physics/ ; https://playcanvas.com/project/643289/overview/vehicle-physics
7. **Animation state graph:** PlayCanvas anim state graph supports idle/walk/run action states, transitions and blending. Must separately implement robust doors/seat interaction state transitions using real clips and attachment points; simply having a GLB does not deliver these. https://developer.playcanvas.com/en/user-manual/animation/
8. **Babylon.js alternative:** Modern browser-based engine with rendering, animation, physics integrations and WebGPU. Evaluate against actual working mobile controls and required pipelines; do not mix two engines for a single gameplay foundation. https://www.babylonjs.com/
9. **Godot browser alternative:** Godot 4 web export is WebGL 2 Compatibility; mobile browser runtime has documented limitations and C# web projects are not supported. https://docs.godotengine.org/en/4.5/tutorials/export/exporting_for_web.html
10. **Asset interoperability:** PlayCanvas recommends GLB for runtime import with animated skeletons, skinning, morph targets, materials and textures; FBX is handled in its Editor via conversion. Source-of-truth should remain original .blend/.fbx and textures, with separate exports and pinned versions. https://developer.playcanvas.com/user-manual/assets/models/building/ ; https://developer.playcanvas.com/user-manual/assets/supported-formats/
11. **Unreal asset interoperability:** Epic documents FBX skeletal mesh imports with animations, materials, UVs and LODs. Shared authored source meshes/rigs/animation concepts can be targeted to both engines with validation. Browser JavaScript physics/gameplay code is **not** automatically reusable as Unreal C++ or Blueprint code. https://dev.epicgames.com/documentation/unreal-engine/fbx-skeletal-mesh-pipeline-in-unreal-engine ; https://dev.epicgames.com/documentation/unreal-engine/fbx-content-pipeline
12. **Real Homewood reference:** Align road network with independent public geospatial datasets, then build original neighborhood assets, not extraction from Google Street View. Compare against user-provided city visual references. https://engage.pittsburghpa.gov/Homewood-mobility-plan

## Candidate foundation, not a completed or approved game
**PlayCanvas + Ammo.js/Bullet + licensed/owned rigged animated GLB assets + independent street-network/traffic navigation + reusable source asset library** is the strongest currently supported *browser-oriented* option for a rebuild. The official raycast-vehicle project and animation state graph are key engineering references, but are not a drop-in GTA-equivalent production game. Need to verify exactly which reusable starter owns pedestrian state machine, car entry/door/seat choreography, navigation and scene streaming; otherwise those integrations must be engineered with proper architecture.

## Shared browser-to-Unreal asset contract
- Geometry source: original editable .blend or DCC source, FBX/glTF exports with proven centimeter/meter conversion and axis mapping.
- Character: proportionate civilian model, named skeleton, fixed root motion strategy, explicit clips `idle`, `walk`, `run`, `enter-car`, `sit`, `drive`, `exit-car`; stable clip event markers and expected retargeting.
- Car: distinct authored body, front/rear axle centers, wheel meshes with correct pivot axes, door hinges, cabin seating transform, steering joint and collision chassis. No blanket `wheel` substring rotation.
- Neighborhood: city centerline road geometry, block/lot source, independently authored walls/shops/porches, coordinate system and tagged materials.
- Portable specifications: named collision layers, event schema, NPC tasks and path graph format can be shared in engine-neutral JSON; each engine uses its own implementation of physics/AI.
- Evidence: screenshot/video + runtime object bounds, animator state and physics debug overlay, screenshots of the same assets successfully imported into both runtimes before claiming portability.
